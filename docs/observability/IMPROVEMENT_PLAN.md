Planning baseline: 2026-10-28; deployment status updated 2026-10-29. Repository: `Kitkitkittt/tele-proxy`; development branch: `codex/1-tele-proxy`; review: [draft PR #13](https://github.com/Kitkitkittt/tele-proxy/pull/13). No Docker image deployment is implied.

## Current objective and authority

Keep the inherited 9Router routing/client contract while completing the policy, durable accounting and metadata-only observability extension. The current operator request adds a controlled 9Router-state migration to tele-proxy, stopping OmniRoute, and deployment at **`tele-proxy.vnibb.xyz` using the Cloudflare CLI**. This supersedes the old `proxy.vnibb.xyz` target and earlier canary-only stop boundary **only for the explicitly requested migration/deployment work**. It is not permission to rewrite unrelated production DNS, expose backend/admin ports, change client approval/model settings, or incur unapproved inference spend.

Older [issue #1](https://github.com/Kitkitkittt/tele-proxy/issues/1), [issue #12](https://github.com/Kitkitkittt/tele-proxy/issues/12), [architecture](ARCHITECTURE.md) and [rollout guide](ROLLOUT_ROLLBACK.md) retain the original target and authorization boundary. Their implementation, privacy, capacity and recovery gates still apply. Read the new hostname here rather than blindly executing old-hostname instructions. The deployment owner must record the new authorized scope and actual outcome in the release/issue evidence; this plan does not declare ingress live.

One gateway owns live credential refresh and mutable state at a time. Development machines share **source through git**, not a writable state directory or synchronized OAuth database. Do not migrate to OmniRoute; retire only its identified service under the current request, preserving its recovery material privately.

## Release gate sequence

1. **Freeze a source checkpoint.** Record full commit, branch, lockfiles, architecture/runtime, existing dirty work and image digest. Preserve unrelated changes. A branch name or `latest` tag is not enough.
2. **Use synthetic isolated state.** Follow [README setup/build/test commands](../../README.md#clone-and-install) and the [production artifact gate](ROLLOUT_ROLLBACK.md#production-artifact-gate-feature-off-at-build-on-at-startup). Never use copied production OAuth during parallel development or restore rehearsal.
3. **Qualify the artifact serially.** Build, focused regression, standalone canary, privacy/secret inspection and benchmark must not contend with each other. Preserve failed/unavailable results. Record the exact commands and artifact identity; historical source tests do not qualify a new native build.
4. **Prove recovery before importing live state.** Use [cold backup/restore](ROLLOUT_ROLLBACK.md#6-consistent-backup-and-isolated-restore-rehearsal) into fresh isolated storage with synthetic/empty gateway credentials. Verify supported adapter integrity, manifest and reconciled ledger/backend retrieval. Preserve source data and rollback material.
5. **Perform the live-owner handoff below.** Stop old ownership before the copied state can refresh credentials. Stage the target offline, keep its bind private, and validate locally before opening the new hostname. No double-running copied credentials as a smoke test.
6. **Configure Cloudflare only for the new target.** Use the installed authorized Cloudflare CLI and the existing account/zone/tunnel arrangement discovered by the deployment owner. Record CLI version and redacted route identity. Route `tele-proxy.vnibb.xyz` to the verified loopback gateway; do not overwrite a shared tunnel file or unrelated ingress/DNS entries. Keep a terminal catch-all rule where the existing tunnel requires it. Never expose metrics, OTLP, database/object-store consoles or monitoring/admin backends through this route.
7. **Verify public behavior, not just CLI exit.** Resolve the intended hostname, verify TLS and the actual origin, check authentication boundaries and authenticated gateway/model access. Use synthetic inference first; live-provider inference requires an authorized route/spend limit and must not shadow production calls. Verify stream/cancellation behavior if a live smoke is authorized. Record HTTP outcomes, time and origin artifact without secrets.
8. **Publish separate status.** Gateway runtime, state migration/OAuth ownership, new-hostname ingress, monitoring, Langfuse, restore and performance each get their own pass/fail/unavailable outcome. If the hostname is not externally exercised, call it configured or pending, not live. Parent deployment verification owns that declaration; this documentation does not supply it.

### Definition of a release record

Keep a redacted record with full source commit/image digest, native runtime/architecture, schema/driver versions, active flags/profiles, chosen state path identifier, service manager identity, new-hostname origin, previous route/config identity, performed commands/exit status, benchmark workload/results and precise unavailable gates. Identify the backup and secret set by private reference, not contents. Record the verified reachable URLs only. Historical reports remain historical rather than being overwritten as if their artifact were current.

## Cross-machine development handoff

### Share code, not a running installation

On the destination workstation:

```sh
git clone --branch codex/1-tele-proxy --single-branch https://github.com/Kitkitkittt/tele-proxy.git
cd tele-proxy
nvm install
nvm use
npm ci
npm --prefix tests ci
# Inspect the source identity before beginning work:
git rev-parse HEAD
git status --short
```

`.nvmrc` currently pins `22.23.4`. Use a clean shell and fresh absolute `DATA_DIR`/temporary `HOME` as in [README](../../README.md#safe-local-development). Build natively on the destination architecture; do not copy `.next`, `node_modules`, SQLite native modules or a development HOME between x64/ARM machines. A running service on another machine is not a reason to point this clone at its live directory.

Before changing machines, the source owner provides a **secret-free handoff note**: full source commit, branch, issue ownership, intended changes, dirty/uncommitted file list, exact last exercised checks and results, blockers, and relevant operational-document links. Commit/push only reviewed source/docs to the authorized branch, or transfer a reviewed source-only patch if not yet committed. Do not use a blanket repository archive that can include ignored `.env`, `.next`, logs, state, captures or credentials. Do not force-push/reset another workstation's work. The receiver checks the full commit and worktree before continuing and installs from lockfiles.

Multiple machines may develop simultaneously against independent synthetic state. Each development process owns its own `DATA_DIR`, HOME, ports and fixture credentials. Never synchronize SQLite through a network drive, rsync loop, cloud file sync or a writable shared volume. Do not run copied OAuth accounts on two hosts even when their DB paths differ.

### Private credential and state transfer, outside git

This is an operator transfer, not the development setup above. Public git carries code and redacted evidence only. An ignored file is not automatically safe to publish, and a private repository is not a credential vault.

1. **Inventory the actual source.** Discover the running 9Router process/service, resolved `DATA_DIR`, adapter/database path and dependent files. Current source uses `DATA_DIR/db/data.sqlite`; older installations may have `db.json`/other legacy files. Do not assume the local checkout describes the deployed data format. Identify service environment files, credential encryption/session/API-key secrets, pseudonym secret if already used, certificates, private tunnel material and any external state dependencies. Record paths/names privately; do not display values.
2. **Choose one destination owner.** Record source and destination service identities, exact matching source/build/schema, selected private absolute state directory, permissions and port. Inspect disk/RAM/CPU, native dependency support and available space for an intact backup plus rollback. Confirm destination autostart and restart policies cannot launch the staged gateway early.
3. **Create the consistent cold snapshot.** Drain traffic and stop the actual 9Router owner, its refresh schedulers/workers and any other process writing its state. Confirm it is stopped. Stop the identified OmniRoute service and its restart owner as requested; preserve its data rather than deleting it. Back up the complete required state under the deployed adapter's cold-copy boundary, including any necessary companion files, not only an arbitrary live SQLite file. The repository Compose `backup.py` applies to its named stopped Compose project; it is not automatically a native/systemd 9Router migration tool.
4. **Transfer privately.** Keep the snapshot, checksum manifest and required matching secret set in a private directory outside the checkout. Use an existing authenticated encrypted channel such as SSH/SFTP, or an approved encrypted archive with its key conveyed separately. Verify host identity and restrict source/destination directories and credential files to the service owner. Never put tokens in command arguments, URLs, shell history, issue attachments, screenshots, chat or diagnostic output. Do not enable shell tracing or print expanded environment/Compose configuration. Do not commit an archive even when encrypted.
5. **Stage offline and validate.** Verify checksums before restore, keep the original snapshot immutable, restore into a fresh dedicated target directory, and set the intended service UID/permissions without blanket host `chown`. Supply the matching JWT/API-key/encryption/pseudonym and other required secrets privately; changing them incidentally can invalidate sessions, stored credentials or identity continuity. Apply only the selected artifact's supported additive migrations. Verify adapter integrity and nonsecret counts/configuration, combo aliases, policy settings and ledger bases. Historical upstream reference costs do not become actual spend on migration.
6. **Start exactly one target owner.** Keep the old owner stopped while the migrated gateway can access real credentials. Start the exact qualified build on private loopback with `TELE_PROXY_ENABLED=1` and the dedicated target state path. Do not enable `TELE_PROXY_CANARY` blindly for production: its suppressed background catalog behavior is a fixture control, not a deployment default. Verify admin/login/API authentication locally; perform authorized inference only within the agreed spend boundary. Do not reseed every production combo with the canary quality policy.
7. **Open only the requested new route.** Complete the Cloudflare and external checks above. Preserve the old production hostname unless a separately justified change is required; report its resulting status honestly. Do not silently change installed client base URLs, model aliases, approval/YOLO settings, MCP/plugins or machine configuration.
8. **Retain recovery without duplicate ownership.** Keep the previous binary/config and cold snapshot privately, with checksums and matching secret-set reference. Confirm the old service and OmniRoute remain stopped according to the chosen service manager, including after restart-policy checks. Delete only staging copies created by this transfer when no longer required; never prune unrelated volumes or remove source recovery data as cleanup.

A shutdown report must identify the exact OmniRoute unit/container and restart policy affected. Port absence alone does not establish that every owner is disabled; a command targeting a guessed service name is not acceptance.

### Rollback after live credentials moved

Stop/drain the target and disable its restart owner **before** resuming any old owner. Preserve the latest target state/credential refresh changes privately: a stale pre-transfer OAuth snapshot may no longer contain valid refresh tokens. Determine whether the old binary can safely read the current additive schema and current credentials; do not claim flag-only rollback without that compatibility evidence. If a matching full-state restore is necessary, use the rehearsed matching binary/schema/secret set and explicitly account for records lost since the snapshot. Do not overwrite fresher tokens with an old backup blindly.

Record and restore only the new hostname's previous route/config when ingress rollback is needed. Do not delete unrelated Cloudflare routes or change the old production hostname by default. Preserve ledger evidence and telemetry state; no `down -v`, volume prune, schema deletion, or invented historical recalculation.
